## What

`ci/submit-pr.sh` writes the PR body, the updated body, and the refusal text with `mktemp`, then
passes those paths to `gh` as `--body-file` / `--input`. Under Git Bash on Windows `mktemp` returns
an MSYS path (`/tmp/tmp.XXXXXXXXXX`), and `gh` is a native Windows binary that cannot resolve MSYS
mount points. Three call sites: lines 155, 191 and 192.

The fix is to hand `gh` a path both worlds can open — `cygpath -w` on the temp path where `cygpath`
exists, or writing the temp files somewhere already native — not to require the caller to export
`TMPDIR`.

## Why

**The failure lands after the push, not before it.** The script resolves HEAD, runs the pipeline,
pushes the verified SHA, and only then calls `gh`. So the failure mode is a pushed branch with no
pull request — the verified-submission invariant is not violated, but the operator is left
half-submitted and has to know that re-running is safe.

This is not theoretical: it happened on 2026-08-27 while submitting
[PR #10](https://github.com/mikeycdavis/HealthAndFitnessAndNutritionStandards/pull/10), and cost two
extra runs of the container gate before the cause was identified.

**Correction, 2026-09-04: `MSYS_NO_PATHCONV=1` IS the trigger.** The claim above was wrong, and it
was wrong because every reproduction recorded below set that variable, so the one condition that
varied was never varied. Run without it, MSYS rewrites the argument into a Windows path on its way to
the native binary and `gh` opens the file:

```
$ f="$(mktemp)"; echo '{}' > "$f"          # /tmp/tmp.CeQ3tQSfSo
$ gh api rate_limit --input "$f"          # {"message": "Not Found", ...}   -> the file opened
$ MSYS_NO_PATHCONV=1 gh api rate_limit --input "$f"
open /tmp/tmp.CeQ3tQSfSo: The system cannot find the file specified.
```

That does not make the defect theoretical, and removing the variable is still not the fix. The Docker
bind mount in `ci/ci.sh` is mangled by the same argument rewriting, so an operator running the
container gate has `MSYS_NO_PATHCONV=1` exported and `submit-pr.sh` inherits it. The defect is
reachable through this repository’s own documented workflow — which is how it was hit. The fix
converts explicitly and so does not depend on the variable in either direction.

## Notes

**Reproduced, read-only, with the file form as the only variable:**

```
$ f="$(mktemp)"; echo '{}' > "$f"
/tmp/tmp.HuZvjSAzt5   ->   C:\Users\Mike\AppData\Local\Temp\tmp.HuZvjSAzt5

$ MSYS_NO_PATHCONV=1 gh api rate_limit --input "$f"
open /tmp/tmp.HuZvjSAzt5: The system cannot find the file specified.     (exit 1)

$ MSYS_NO_PATHCONV=1 gh api rate_limit --input "$(cygpath -w "$f")"
gh: Not Found (HTTP 404)                                                 (exit 1)
```

The second invocation reaches the API, so the file was opened. The only difference is the path form,
which rules out permissions, a missing file, and the `gh` authentication state.

`gh` at `F:\Program Files\GitHub CLI\gh.exe`; bash at `F:\Program Files\Git`.

**Workaround until this is fixed:** `export TMPDIR="C:/Users/Mike/AppData/Local/Temp"` before calling
`ci/submit-pr.sh`. That is what unblocked PR #10, and it is a caller-side workaround rather than a
fix — a fresh checkout on another Windows machine hits this again.

**`ci/submit-pr.ps1` is not affected** and is not evidence that the bash path works; the two wrappers
are covered separately, and the PowerShell tests skip everywhere the bash suite runs.

**Deliberately not filed as part of ST-11.** ST-11 is a CI matrix change; this is a defect in the
submission wrapper found while using it. Fixing it on that branch would have moved a head that was
already verified and under review.

Any fix needs a test that fails without it. The existing `LOCAL_CI_COMMAND` / `GH_COMMAND` seams in
`test/local-ci.test.mjs` already drive the real script against a stub `gh`, so the assertion has a
home: the stub can refuse a path it cannot open, which is exactly what the real binary does.

## Fixed 2026-09-04

`native_path()` in `ci/submit-pr.sh` converts with `cygpath -w` where cygpath exists and is the
identity everywhere else, applied at both `--body-file` call sites (`pr create` and `pr edit`). The
conversion is explicit, so the result does not depend on whether MSYS is rewriting arguments.

Two regression tests in `test/local-ci.test.mjs` drive the real script through the existing
`LOCAL_CI_COMMAND` / `GH_COMMAND` seams with `MSYS_NO_PATHCONV=1` set, covering both call sites.
Red before the fix, green after:

```
the native CLI could not open the body file at /tmp/tmp.d8NHVUWr7v
the native CLI could not open the rewritten body at /tmp/tmp.lgkUPyQi7H; submit-pr.sh exited 0
```

That second line is the defect stated exactly: exit 0, branch pushed, no pull request.

**Why the existing seam coverage did not already catch this.** The `gh` stub the other tests use is a
bash script that reads the body with `cp`. `cp` is an MSYS program and resolves `/tmp` perfectly, so
the stub could do something the binary it stood in for cannot, and reported success for a defect. The
new stub hands the path to `process.execPath` — the same native `node.exe` running the suite — which
fails on an MSYS path for the same reason `gh.exe` does. A stub more capable than the real tool is a
stub that certifies its own defects.

The clean-tree refusal is untouched and was not stepped around by weakening it: the stub lives outside
the work tree, because an untracked file inside it is a dirty tree and `submit-pr.sh` correctly
refuses to verify one. It refused during development, which is the guarantee working.
