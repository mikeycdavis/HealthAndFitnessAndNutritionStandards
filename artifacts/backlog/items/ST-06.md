## What

Verify the certification candidate against the recorded procedure, then remove the
`|| [ $? -eq 4 ]` allowance from CI, move `VERSION` off `1.0.0-dev`, re-run the full gate, and tag
`v1.0.0`.

## Why

Adoption must pin an immutable release. Until the tag exists there is nothing an adopter may
legitimately pin to.

## Notes

**Complete.** `v1.0.0` is an annotated tag at `570c45b`, pushed. The three pre-tag conditions were
established in order and none was inferred from another: a genuinely executed green Actions run
(31625046364) on that exact commit, a fresh independent certification pass against that same commit,
and a final check that HEAD had not moved and no attestation had gone stale. The tag was created only
on the accountable person's explicit authorization.

Independent certification passed against `9809afc`, which authorized this item to begin. The
mechanics then ran as their own commit: `VERSION`, `package.json`, and `standardVersion` moved to
`1.0.0`, and CI's `|| [ $? -eq 4 ]` allowance and its transitional comment came out. The full gate is
green locally.

**The tag is not cut, and `83d799b` can no longer carry it.** Actions billing was fixed, the run on
`83d799b` executed for the first time, and it FAILED — at the Tests step, not on infrastructure.
`npm test` used a glob that only Node 21 and later expands, while CI pins Node 20 and `engines` says
`>=18`, so the suite had never executed anywhere but the maintainer's machine. Fixed by naming the
test files explicitly, with a guard that fails if a test file on disk is not named in the command.

That is the argument for treating CI as an enforcement surface, made concrete: tagging around a
runner that could not start would have pinned 1.0.0 to a commit whose tests cannot run in the
environment meant to enforce them.

The candidate is now the commit that fixed it. Obtain a green Actions run on that commit, re-run the
certification pass against it — the previous pass certified `83d799b`, which is not the commit that
will be tagged — then tag `v1.0.0`.

Do not tag to make this item close, and do not weaken the workflow to obtain a green run.

The verification order is itself the control, and it is recorded in
[`artifacts/release-review/dispositions.md`](../../release-review/dispositions.md):

> diff against `7f59f8b` → explain every consequential change → verify evidence-chain integrity →
> compare per-rule states → compare verdict → release mechanics

The verdict is an output, not the release evidence. A `COMPLIANT` verdict is not evidence that an
unexplained diff is acceptable, and a matching predicted state is not either.

Eight post-baseline commits are now known, and the certification pass explained all of them:
`cc0c6de` (BACKLOG.md only), `6c2f447` (dispositions.md only), `6352108` (the backlog and its
certification record), `ad6bdcb` (attestations recorded — **do not certify this commit**), `7b650f2`
(the withdrawal), `eb9a0f8` (the valid attestations), `9809afc` (the CI comment correction), and the
release-mechanics commit. Only `ad6bdcb`, `7b650f2`, and `eb9a0f8` move verdict inputs. The baseline
does not advance for any of them.

`9809afc` is worth its own note: the defect it fixed was not in the diff at all. The workflow had not
changed since `7f59f8b`. Diff-first protects against unexamined change; it cannot establish that
unchanged baseline content was ever correct.

`ad6bdcb` is the worked demonstration that a candidate can match every predicted per-rule state and
still be uncertifiable. Explain the provenance of a verdict-affecting input, not only its shape.
