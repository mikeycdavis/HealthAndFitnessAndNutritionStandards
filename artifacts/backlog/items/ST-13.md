## What

Make `ci/submit-pr.sh` refresh the `## Local CI` block of an existing pull request body, so the block
names the commit the run actually verified rather than the commit that happened to open the request.

## Why

The script writes that block on the create path only. On the existing-PR path it prints the new
verification to the terminal, says `No body was rewritten`, and leaves the old table in place. The
comment above that branch explains the reasoning, and the reasoning is right as far as it goes: a body
may have been edited by a human since, and clobbering it would destroy their work.

What it misses is that the block is not neutral when it goes stale. It says **Verified commit**, and a
reviewer reading the request is told that an earlier object is the verified subject of the code in
front of them. Found by independent review of PR #2, which by then carried `f56c7e1` under a table
naming `b70d798` — two commits and one remediation earlier, describing a design the branch no longer
had.

That is the repository's own recurring failure class, on the surface a reviewer reads first: not a
false green, but a true green pinned to the wrong thing. `ci/run-checks.sh` documents the same shape
arriving twice already.

## How

The block is delimited and entirely script-authored — everything from `---` before `## Local CI` to
the end of the body — so the fix does not require touching a human's prose. Replace that span, keep
everything above it byte-identical, and write the result back with `gh pr edit --body-file`.

Two cases need deciding rather than assuming:

- **The body has no such block** (a request opened by hand, or by an earlier version of the script).
  Appending is right; silently doing nothing is not.
- **The body has more than one**, or one a human has edited. Refusing loudly and printing the intended
  block beats guessing, for the same reason `--force-overwrite` names an exact path.

Preserving the superseded rows rather than deleting them is worth considering: a request whose body
shows what was verified at each push is a better record than one showing only the latest, and this
repository already prefers keeping refuted content beside its correction to replacing it.

## Acceptance

- A falsifier committed failing first: a body carrying a `## Local CI` block for commit A, resubmitted
  at commit B, must not still assert A.
- Prose above the block survives a resubmission byte-identically.
- A body with no block, and a body whose block cannot be located unambiguously, each have a defined
  outcome, and the second is a refusal rather than a rewrite.
- No path in the script can leave a body asserting a commit that is not the one the run verified.

## Done — 2026-08-16

`ci/pr-evidence.mjs` composes the block and is the only thing that replaces it; both `submit-pr.sh`
and `submit-pr.ps1` call it, so the two wrappers cannot drift into writing different evidence for the
same run. **The PowerShell wrapper had the same defect and was worse** — it did not even print the
block it was failing to write — which is why the fix is a shared module rather than an edit to the
shell script the review happened to name.

Every acceptance criterion above is met, each by a test in `test/pr-evidence.test.mjs` and
`test/local-ci.test.mjs`. Superseded runs are kept beneath the current one rather than dropped.

**One existing test had to be rewritten, and it is worth recording why.** The submission test ended
with `assert.ok(!existsSync("gh-args.txt"), "no second PR may be created")` — using "the GitHub CLI
was never invoked" as a proxy for "no second pull request was created". Those were the same fact only
while this path did nothing but print, and the doing-nothing *was* the defect. So the proxy was
quietly pinning the defect in place. It now asserts `pr edit` and not `pr create` directly, plus
three properties it could not previously see. Nothing was weakened to make the change land; the test
was measuring the wrong thing, and a test that pins a defect passes for exactly as long as nobody
fixes it.
