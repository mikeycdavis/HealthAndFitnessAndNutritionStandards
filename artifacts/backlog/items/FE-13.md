## What

An adopter claiming to use `v1.0.0` must demonstrably be evaluated against the exact immutable
release. Where that cannot be established, evaluation fails closed rather than silently substituting
a branch, a moving ref, a local checkout, or a cached copy whose identity is no longer proven.

No tooling may treat `1.0.0-dev`, `main`, or a certification candidate as adoptable.

## Why

Certification is what makes a version adoptable, not completeness. The implementation was finished at
`cdda7d6` and the repository still correctly reported `NOT_EVALUATED` for weeks afterwards.

**Version equality is not identity equality.** `standardVersion: "1.0.0"` in an adopter's policy
establishes what that project *claims* to use. It establishes nothing about which bytes were
evaluated. This feature closes only when the second is proven.

## Acceptance criteria

| Case | Required behaviour |
| --- | --- |
| Exact `v1.0.0` tag, resolving to `570c45b` | Accept |
| A moving branch such as `main` | Reject |
| A different tag or commit presented as `v1.0.0` | Reject |
| A local standards checkout substituted for the release | Reject |
| A cached copy whose identity is no longer proven | Reject |
| Tag resolves correctly but evaluated content differs | Reject |
| Release identity cannot be established at all | Fail closed |
| Source unavailable before identity can be proven | Fail closed, never silent fallback |

**Completion property.** This item cannot complete while any of its three falsifiers is still marked
`todo`. Completion requires converting all three — **unchanged** — into ordinary passing regression
tests. They may not be deleted, weakened, rewritten to assert something easier, or moved out of the
default test run. A `todo` that disappears for any reason other than the false green having been
removed is the failure this repository names in Standard 42.

**Three concepts are currently collapsed, and a version-string comparison would not separate them:**

1. what version the adopter **claims**;
2. what pack the executing CLI **is**;
3. what standards bytes **actually produced the verdict**.

`standardVersion: loaded.policy.standardVersion ?? version` makes the first masquerade as the second,
and loading the catalog from `ROOT` means neither establishes the third. Any proposal that compares
two version strings should be rejected on those grounds alone. What is needed is an authority identity
with enough provenance to prove the evaluated pack *is* the immutable release the adopter selected.
The falsifiers determine the mechanism from there — not the other way round.

## Notes

Requirement 6 of EP-03, and the first item in the agreed order. It comes before FE-14 (which
automates adoption) and FE-09 (which hardens it against bypass) on purpose: anti-bypass controls
designed around an unproven bootstrap contract would harden the wrong shape.

**The falsifier came first, and it is committed:**
[`test/release-identity.test.mjs`](../../../test/release-identity.test.mjs). Three assertions, all
failing, reproducing the false green before any remedy was designed. That ordering is not ceremony —
both defects this release actually shipped and had to correct were invisible to reasoning and visible
only to execution.

**What the falsifier established.** The claim is not merely unverified; it is the value the tool
reports back. `scripts/standards.mjs:615` reads:

```js
standardVersion: loaded.policy.standardVersion ?? version
```

The adopter's own assertion wins outright, and the catalog is loaded from `ROOT` — wherever the CLI
happens to live — with no identity check anywhere in the path. A pack whose `VERSION` says
`0.0.0-substituted`, and one of whose prohibitions has had its verbatim source line reworded, still
produces a report stating the adopter was evaluated against 1.0.0. Deleting `VERSION` entirely
changes nothing: the code defaults to the string `"unknown"` and carries on.

Note which existing guard would have caught that reworded line — `npm run fidelity` — and that
`check` never asks it. The guards protect this repository's own maintenance. Nothing protects an
adopter from the pack it is actually running.

**The falsifiers are marked `todo` rather than left red.** They run on every CI run and print exactly
what they assert, but they do not turn `main` red, because a knowingly-red enforcement surface teaches
everyone who sees it that red means nothing. Removing the marker is part of the remedy, not a
follow-up: this item does not close while it is still there.

**Not yet designed, deliberately.** Whatever the mechanism turns out to be — a release digest, a
resolved tag recorded in the policy, a content hash over the catalog — it has to surface in the JSON
envelope, or the distinction between a genuine and a substituted evaluation exists only in the
operator's head.

**The next step is not "implement version pinning."** It is: specify what constitutes authoritative
release identity, then design the smallest mechanism that makes all three reproduced false greens
impossible and fails closed when that identity cannot be established. Do it against a working remote
CI, so the remedy is tested in the environment that enforces it — the last two defects this
repository shipped were both invisible until something actually ran.
