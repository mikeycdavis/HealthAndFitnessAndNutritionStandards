## What

An adopter claiming to use `v1.0.0` must demonstrably be evaluated against the exact immutable
release. Where that cannot be established, evaluation fails closed rather than silently substituting
a branch, a moving ref, a local checkout, or a cached copy whose identity is no longer proven.

No tooling may treat `1.0.0-dev`, `main`, or a certification candidate as adoptable.

## Why

Certification is what makes a version adoptable, not completeness. The implementation was finished at
`cdda7d6` and the repository still correctly reported `NOT_EVALUATED` for weeks afterwards.

**Version equality is not identity equality.** `standardVersion: "1.0.0"` in an adopter's policy
establishes what that project *claims* to use. It establishes nothing about which bytes were
evaluated. This feature closes only when the second is proven.

## Acceptance criteria

| Case | Required behaviour |
| --- | --- |
| Exact `v1.0.0` tag, resolving to `570c45b` | Accept |
| A moving branch such as `main` | Reject |
| A different tag or commit presented as `v1.0.0` | Reject |
| A local standards checkout substituted for the release | Reject |
| A cached copy whose identity is no longer proven | Reject |
| Tag resolves correctly but evaluated content differs | Reject |
| Release identity cannot be established at all | Fail closed |
| Source unavailable before identity can be proven | Fail closed, never silent fallback |
| **Correct tag + correct `VERSION` + modified standards file** | **Reject** |

That last case is the control. A remedy that compares version strings, or that resolves the tag and
stops there, passes every other row and fails this one — which is the point: it separates artifact
identity from labels.

**Completion property.** This item cannot complete while any of its four falsifiers is still marked
`todo`. Completion requires converting all four — **unchanged** — into ordinary passing regression
tests. They may not be deleted, weakened, rewritten to assert something easier, or moved out of the
default test run. A `todo` that disappears for any reason other than the false green having been
removed is the failure this repository names in Standard 42.

**Three concepts are currently collapsed, and a version-string comparison would not separate them:**

1. what version the adopter **claims**;
2. what pack the executing CLI **is**;
3. what standards bytes **actually produced the verdict**.

`standardVersion: loaded.policy.standardVersion ?? version` makes the first masquerade as the second,
and loading the catalog from `ROOT` means neither establishes the third. Any proposal that compares
two version strings should be rejected on those grounds alone. What is needed is an authority identity
with enough provenance to prove the evaluated pack *is* the immutable release the adopter selected.
The falsifiers determine the mechanism from there — not the other way round.

## The authority model

> A standards evaluation is **release-identified** only when the evaluator can prove that the exact
> standards tree it is using is the tree designated by the immutable release reference declared by
> the adopter.

Three stages, which stay separate in the implementation because collapsing them is how the defect
arose in the first place:

| Stage | Question |
| --- | --- |
| Resolution | What immutable object does `v1.0.0` designate? |
| Materialisation | What bytes are we about to evaluate? |
| Verification | Are those bytes exactly the object resolved for `v1.0.0`? |

The policy's `standardVersion: "1.0.0"` is the **requested** identity. It is not evidence.

**Git object identity, not a content manifest of our own.** `v1.0.0` already designates a commit and
a tree under a cryptographic identity that predates this repository. Inventing a second normative
source of truth would mean maintaining it, agreeing it with adopters, and defending it — for a
property Git already provides.

The authority should ultimately produce something shaped like this. The field names can change; the
concepts cannot:

```text
requestedRelease: v1.0.0
resolvedCommit:   570c45b...
resolvedTree:     <git tree oid>
evaluatedTree:    <git tree oid>
identity:         MATCH
```

Both halves are required. `VERSION == 1.0.0` is a label. `HEAD == commit(v1.0.0)` is insufficient
while the worktree can hold modified or untracked standards bytes. The finding is about which bytes
produced the verdict.

**Fail closed before loading rules**, whenever: the tag cannot be resolved; the ref is not immutable
or not permitted; the object cannot be proven; the evaluated material is not the resolved tree; a
required standards file is modified; a substituted local pack has no matching identity; `VERSION` is
missing; `VERSION` disagrees with the resolved release; or the policy claims a release that is not
the one evaluated.

**Order matters: identity before rule evaluation.** Do not produce a substantive compliance verdict
and then append that identity was unverified. Identity failure means the evaluation has no authority
— there is nothing to append it to.

### Two scope distinctions that would otherwise be got wrong

**The adopter's working tree may be dirty.** Adopters evaluate in-development code; that is the
normal case, not a violation. The identity check applies to **the standards pack material**, never to
the adopter's own product code. The tempting implementation — `git status --porcelain` over the whole
repository — is wrong for exactly this reason.

**A local copy is not prohibited for being local.** The rule is that local material is acceptable
only if its release identity can be independently re-established. That leaves room for caching and
vendoring without weakening anything:

> **Materialisation may reuse bytes; it may not reuse trust.**

A cache hit can avoid a download. It cannot avoid verifying that the cached material still
corresponds to the immutable release.

## Notes

Requirement 6 of EP-03, and the first item in the agreed order. It comes before FE-14 (which
automates adoption) and FE-09 (which hardens it against bypass) on purpose: anti-bypass controls
designed around an unproven bootstrap contract would harden the wrong shape.

**The falsifiers came first, and they are committed:**
[`test/release-identity.test.mjs`](../../../test/release-identity.test.mjs). Four cases, all failing,
reproducing the false green before any remedy was designed. That ordering is not ceremony —
both defects this release actually shipped and had to correct were invisible to reasoning and visible
only to execution.

**What the falsifier established.** The claim is not merely unverified; it is the value the tool
reports back. `scripts/standards.mjs:615` reads:

```js
standardVersion: loaded.policy.standardVersion ?? version
```

The adopter's own assertion wins outright, and the catalog is loaded from `ROOT` — wherever the CLI
happens to live — with no identity check anywhere in the path. A pack whose `VERSION` says
`0.0.0-substituted`, and one of whose prohibitions has had its verbatim source line reworded, still
produces a report stating the adopter was evaluated against 1.0.0. Deleting `VERSION` entirely
changes nothing: the code defaults to the string `"unknown"` and carries on.

Note which existing guard would have caught that reworded line — `npm run fidelity` — and that
`check` never asks it. The guards protect this repository's own maintenance. Nothing protects an
adopter from the pack it is actually running.

**The falsifiers are marked `todo` rather than left red.** They run on every CI run and print exactly
what they assert, but they do not turn `main` red, because a knowingly-red enforcement surface teaches
everyone who sees it that red means nothing. Removing the marker is part of the remedy, not a
follow-up: this item does not close while it is still there.

**Not yet designed, deliberately.** Whatever the mechanism turns out to be — a release digest, a
resolved tag recorded in the policy, a content hash over the catalog — it has to surface in the JSON
envelope, or the distinction between a genuine and a substituted evaluation exists only in the
operator's head.

## Progress

**Stage 1, resolution, is implemented and independently tested.**
[`scripts/release-identity.mjs`](../../../scripts/release-identity.mjs) exports `resolveRelease()`
and nothing consumes it yet — deliberately. A primitive that cannot state precisely why it refused is
not ready to be trusted by something that refuses on its behalf, so the failure taxonomy is tested
first: `not-a-release-version`, `no-repository`, `tag-not-found`, `ambiguous-ref`, `unannotated-tag`,
`unresolvable`. 16 tests in
[`test/release-resolution.test.mjs`](../../../test/release-resolution.test.mjs), all passing.

Decisions made in that slice, both open to reversal:

- **A lightweight tag is refused.** Neither tag kind is immutable against a determined push, but only
  an annotated tag records that it was ever made. A release reference should carry its own provenance.
- **A tag shadowed by a branch of the same name is `ambiguous-ref`, not a resolution.** `git rev-parse
  v1.0.0` would silently pick one, and one of the two candidates is a moving ref.

**A finding about the enforcement environment.** `actions/checkout@v4` fetches one commit and no tags,
so `refs/tags/v1.0.0` does not exist on CI even though it exists on the remote. Resolution correctly
refuses there with `tag-not-found` — identity that cannot be proven is not established — but it means
**verification cannot run under the current workflow** without `fetch-depth: 0` or an explicit tag
fetch. Not fixed here: changing the workflow to suit a primitive nothing yet depends on is the wrong
order, and it belongs with the slice that first needs it.

**Stage 2, materialisation, is implemented and independently tested.**
[`scripts/release-material.mjs`](../../../scripts/release-material.mjs) exports `materialise()` and
`blobOid()`, and nothing consumes them yet either. It answers only *what bytes are we about to
evaluate* — it takes no version, consults no tag, and compares nothing. `materialise()` succeeding
means "these are the bytes", never "these are the right bytes". 14 tests in
[`test/release-materialisation.test.mjs`](../../../test/release-materialisation.test.mjs).

Decisions made in that slice:

- **Git blob identity, computed locally.** A file's identity is the object id Git would record:
  `sha1("blob " + length + "\0" + contents)`. Stage 3 has to compare these bytes against a Git tree;
  any other hash would mean inventing the second normative identity this item already ruled out and
  then converting between the two at exactly the point where a mistake is invisible. The claim is
  tested against `git hash-object` rather than against itself.
- **The material boundary is a declared, reviewed list** — `MATERIAL`: `VERSION`, `PROHIBITIONS.md`,
  the two reviewed inventories, `rules/`, `schemas/`, `scripts/`, `standards/`, `templates/`. Every
  path whose bytes can change a verdict; prose about the pack is outside it. A boundary that includes
  everything fails on every unrelated edit and is then widened until it means nothing.
- **The list is checked against the code, not against itself.** A test extracts every
  `path.join(ROOT, "…")` the CLI reads and asserts the boundary covers it, so a new read cannot
  quietly leave material out — a false green reintroduced by omission rather than by tampering.
- **`materialise()` takes a pack root and nothing else.** It is structurally incapable of reading the
  adopter's tree, which is a stronger guarantee than remembering not to. The dirty-adopter negative
  control asserts this directly.
- **Symlinks are refused, not followed.** A link supplies bytes from outside the material under a path
  inside it — the substitution this feature exists to detect, arriving through the mechanism meant to
  detect it. Windows will not create one without privileges, so the strong branch runs on CI and the
  local branch asserts the precondition; neither is a skip.

**The limit worth stating rather than hiding.** `scripts/` is material, so a substituted evaluator
fails verification like any other file — but the code doing the checking is the code being checked,
and a substituted pack that also removed the check would simply not run it. Materialisation raises the
cost of tampering; it cannot make an evaluator self-guaranteeing, and no arrangement of this code
could. That property belongs to the adopter fetching a pack rather than being handed one, which is
FE-14, not a hash.

**Next: stage 3, verification** — are these bytes exactly the object stage 1 resolved — and only then
wiring into `check`. Not one combined version-validation function: that would collapse resolution,
filesystem checks, and verdict semantics back together, which is the shape the defect came from.
Verification is also the first slice that genuinely needs tags on CI, so the `fetch-depth` change
recorded above belongs with it.
