## What

Make canonical-pack origin depend on verifying an immutable release's signature against a trust
anchor supplied from **outside** the pack being evaluated, rather than on the tag resolving to a
recorded commit oid.

## Why

[ADR 0009](../../adr/0009-self-maintenance-is-a-distinct-outcome.md) closed the escape that
independent review found — an adopter can no longer acquire self-maintenance by copying the evaluator
into a directory they control — and named the residual it did not close:

> A fork of this repository possesses every byte the original does — the certified tag, the recorded
> oid, the lineage, and the file explaining them — so no check running inside the evaluator
> distinguishes a fork from the pack.

The residual is bounded rather than dangerous. What eligibility buys is a `SELF_MAINTENANCE` outcome:
not a compliance verdict, from a command an adopter's pipeline does not run, carrying no authority
over anybody's adoption of anything. A fork that satisfies the conditions has gone to considerable
trouble for a result that fails every gate it would want to pass.

FE-13's original acceptance criterion — no adopter can satisfy `packSelfMaintenance` structurally —
was retired by the owner on 2026-08-16 and replaced with a boundary that names this residual and
assigns it here. Both records carry the approved wording: ADR 0009, and [FE-13](FE-13.md)'s
acceptance criteria. This item is where that criterion goes to be met, and until it is met nothing may
report FE-13 as having established fork exclusivity.

A signature is the only thing that would actually close it, because it is the only fact about the
release that cannot be copied along with the bytes — **provided the key it is checked against cannot
be copied along with the bytes either.**

## The custody decision, and the constraint that came with it

The blocking question — who holds the key — was answered by the owner on 2026-08-16 and is recorded
in full in [ADR 0010](../../adr/0010-release-signing-custody-and-an-external-trust-anchor.md):
Michael Davis as the accountable human release owner; the private key human-controlled, never
committed, never generated by the pack, never available to ordinary CI; **the trust anchor supplied
externally to the pack being evaluated**; no configured key is `NOT ESTABLISHED` rather than skipped;
a wrong or untrusted signature fails closed; rotation is a governance event; agents may verify and
prepare but never hold the signing authority.

The externality constraint is the part that changes the implementation rather than the paperwork. A
`scripts/trusted-key.json` living inside this repository is replaced by a fork along with everything
else, after which the fork signs its own release, verifies successfully, and reports a cryptographic
proof of nothing. That design would pass every obvious test.

## Acceptance

- **The falsifier, committed failing first.** Copy the entire repository, replace its trust
  configuration with an attacker-controlled public key, create a correctly signed release using the
  attacker's matching private key, and prove verification still rejects it because the authoritative
  anchor came from outside the fork. The fork in this test is competent: it signs correctly and is
  internally consistent, and fails on the one fact that is not its to change. **An implementation
  that passes only because the fork did not think to replace the key file has not met this criterion.**
- A fork with the full lineage and no valid signature is refused canonical origin.
- Verification failure, wrong-key, and verification-unavailable are distinct outcomes, as
  contradicted and unavailable already are in `scripts/pack-lineage.mjs`. Unavailable must not pass,
  and must never be reported as skipped.
- `scripts/certified-releases.json` records per release whether it was signed under this regime and
  against which key identity, so a release predating it says so rather than being silently treated as
  unsigned-therefore-fine or unsigned-therefore-broken.
- ADR 0009's "what is not claimed" section is revised to say what the new mechanism does claim, and
  the schema description for `packSelfMaintenance` with it. Neither may claim more than the
  implementation supports — the failure that opened this line of work. In particular neither may
  claim origin for an operator who took the anchor from the pack.
- Every origin-dependent assertion in this codebase goes through one contract that refuses unless
  `origin.status === ESTABLISHED`, and no such assertion reads `status` or `workingTreeStatus`
  instead. The point of a single contract is that a future consumer cannot make the claim by
  accident; appending the field and trusting callers to read it is what ADR 0009's property 2 already
  cost once.
- The mechanism (GPG, SSH signing, minisign, other) is chosen after the falsifier exists, and the
  choice is justified against it.

## Where the requirement binds — decided

The owner decided on 2026-08-16: **`maintain` reports origin; it does not require it. Anything that
claims canonical origin must require it.** The full statement and the reason are in ADR 0010.

Eligibility for `maintain` therefore stays lineage-based, because `maintain` is not an
origin-authority operation — it answers whether this working tree satisfies the standards it
publishes, and making that answer depend on release-owner credentials would put ordinary development
behind trust configuration contributors correctly should not hold.

The envelope carries origin as a named state with a reason, never a boolean:

```
status: SELF_MAINTENANCE
workingTreeStatus: COMPLIANT

origin:
  status: ESTABLISHED | NOT_ESTABLISHED
  reason: trust-anchor-absent | untrusted-signer | invalid-signature | release-unavailable
  trustedKey: ...
```

`originVerified: false` is rejected: a boolean lets a caller collapse "checked and rejected", "could
not check", and "no anchor was supplied" into one branch, and those three are the distinction the
mechanism exists to make.

The "field nobody reads" risk is answered structurally rather than by hoping. Any API making an
origin-dependent assertion goes through a contract that requires `ESTABLISHED`; reading `status` or
`workingTreeStatus` alone can never produce a positive canonical-origin result, and a test says so.

## The three acceptance tests, written before the plumbing is chosen

1. **No anchor.** Legitimate pack lineage, no externally supplied anchor → maintenance can succeed,
   origin is `NOT_ESTABLISHED / trust-anchor-absent`.
2. **Attacker fork.** Full fork carrying an attacker-controlled in-repo key and a correct signature
   over it, evaluated against an independently trusted real fingerprint → maintenance may run, origin
   remains `NOT_ESTABLISHED`.
3. **Origin-dependent consumer.** Feed either of those outputs into the canonical-origin assertion
   path → it must refuse.

Together with the substitution falsifier above these preserve both invariants: development remains
achievable without release authority, and origin authority remains impossible without externally
supplied trust.

## Landed so far — the contract, not the cryptography

`scripts/pack-origin.mjs` holds the origin states, the five reasons, and `assertCanonicalOrigin` —
the one door every origin-dependent assertion goes through. The verifier is injected, so the module
is complete without a mechanism and the mechanism can be chosen against the falsifier rather than
around an existing implementation.

Two properties are worth naming because neither is visible in a passing happy path:

- **The anchor is checked before anything else**, which makes "no anchor supplied" unreachable from
  every later branch. No verifier — including a hostile one a fork supplies — can produce
  `ESTABLISHED` for an operator who never configured trust.
- **The module imports no filesystem access at all**, and a test asserts the absence structurally. A
  future edit adding "fall back to `scripts/trusted-key.json` when no anchor is supplied" is the
  rejected design, and it would pass every behavioural test here because it only makes the happy path
  easier. A module that cannot open a file cannot be talked into it.

The tests were written after the module rather than before it, which is recorded in the test header
rather than glossed: they did not fail first against an absent implementation, and four mutations
against the committed module are the compensating evidence. Two mutation results contradicted the
prediction and both are recorded as observed — including one showing a test passing for a reason
other than the one it was written for.

### Still to do

- Choose the mechanism (GPG, SSH signing, minisign) and supply the verifier, justified against the
  substitution falsifier.
- Decide how the anchor reaches the CLI from an operator-controlled store, which is the one remaining
  place the externality can be lost — an environment variable naming a path inside the pack would
  hand it back.
- Wire `origin` into the `maintain` envelope. Deliberately not done yet: it is an output-contract
  change (`schemaVersion` would move again), and the only value it could carry today is
  `verification-unimplemented`. One contract change when the field can say something is better than
  two.
- Revise ADR 0009's "what is not claimed" and the `packSelfMaintenance` schema description once the
  mechanism exists, per the acceptance criteria above.

## Why it was not done sooner

Two of the three original reasons are discharged. The key-management commitment is decided (ADR
0010). The temptation to ship a `git verify-tag` call that passes when no key is configured is now
forbidden explicitly rather than resisted informally.

The third stands and is not a blocker: **the certified releases predate it.** `v1.0.0` is unsigned and
cannot be signed now without re-tagging, which is the moving-reference-wearing-an-immutable-name
problem FE-13 detects ([ADR 0008](../../adr/0008-authenticity-guarantees-are-not-retroactive.md)).
Signing it retroactively would not help anyway: a fork copies a genuine signed historical tag as
easily as an unsigned one. The property becomes strongest at the first *new* release signed under
this regime, from which point a fork can copy already-authorized releases but cannot mint a new
authoritative one. Verification therefore establishes a floor at the first signed release, exactly as
FE-13's own mechanism does.
