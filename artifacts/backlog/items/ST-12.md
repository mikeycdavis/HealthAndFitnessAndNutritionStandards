## What

Make eligibility for `standards maintain` depend on verifying the certified release tag's signature
against a key the project holds, rather than on the tag resolving to a recorded commit oid.

## Why

[ADR 0009](../../adr/0009-self-maintenance-is-a-distinct-outcome.md) closed the escape that
independent review found — an adopter can no longer acquire self-maintenance by copying the evaluator
into a directory they control — and named the residual it did not close:

> A fork of this repository possesses every byte the original does — the certified tag, the recorded
> oid, the lineage, and the file explaining them — so no check running inside the evaluator
> distinguishes a fork from the pack.

The residual is bounded rather than dangerous. What eligibility buys is a `SELF_MAINTENANCE` outcome:
not a compliance verdict, from a command an adopter's pipeline does not run, carrying no authority
over anybody's adoption of anything. A fork that satisfies the conditions has gone to considerable
trouble for a result that fails every gate it would want to pass. That is why this is deferred rather
than open.

The deferral is not an omission noticed later. FE-13's original acceptance criterion — no adopter can
satisfy `packSelfMaintenance` structurally — was retired by the owner on 2026-08-16 and replaced with
a boundary that names this residual and assigns it here. Both records carry the approved wording:
ADR 0009, and [FE-13](FE-13.md)'s acceptance criteria. This item is where that criterion goes to be
met, and until it is met nothing may report FE-13 as having established fork exclusivity.

A signature is the only thing that would actually close it, because it is the only fact about the
release that cannot be copied along with the bytes.

## Why it is not done now

Three reasons, in order of weight.

1. **A check that passes when no key is configured is worse than no check.** `git verify-tag` on a
   machine with no keyring reports failure; on a machine with the wrong keyring it reports failure;
   the temptation in both cases is a fallback, and the fallback is the false green this whole feature
   exists to remove. Adding it half-configured would reintroduce the defect under a stronger-sounding
   name.
2. **It is a key-management commitment, not a code change.** Somebody has to hold the signing key,
   sign each release with it, publish the public key somewhere adopters can obtain independently of
   the repository, and rotate it. None of that exists here yet, and deciding it is the owner's call.
3. **The certified releases predate it.** `v1.0.0` is unsigned and cannot be signed now without
   re-tagging, which is the moving-reference-wearing-an-immutable-name problem FE-13 detects
   ([ADR 0008](../../adr/0008-authenticity-guarantees-are-not-retroactive.md)). Signature
   verification would therefore establish a floor at the first signed release, exactly as FE-13's own
   mechanism does — which is the correct shape, and worth saying in advance so it is not discovered
   as a surprise a second time.

## Acceptance

- The signing key, its custodian, and its publication route are decided and recorded before any code
  is written.
- Verification failure and verification-unavailable are distinct outcomes, as contradicted and
  unavailable already are in `scripts/pack-lineage.mjs`. Unavailable must not pass.
- A falsifier committed failing first: a fork with the full lineage and no valid signature is refused
  eligibility.
- ADR 0009's "what is not claimed" section is revised to say what the new mechanism does claim, and
  the schema description for `packSelfMaintenance` with it. Neither may claim more than the
  implementation supports — the failure that opened this line of work.
