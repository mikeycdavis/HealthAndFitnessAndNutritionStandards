## What

Run the CI job as a matrix across the Node versions `package.json` declares support for — currently
18, 20, 22, and 24 — instead of the single pinned 20. Bump `actions/checkout` and `actions/setup-node`
to v5 with it.

## Why

`engines` says `>=18`. CI exercises one version. Everything between the two is asserted rather than
demonstrated.

That gap is not theoretical here. It hid a defect for the entire life of the repository: `npm test`
was `node --test "test/*.test.mjs"`, and glob expansion inside `--test` only arrived in Node 21. On
the maintainer's Node 24 the suite ran; on every Node in the declared range it found nothing and
exited 1. The suite had never executed in CI at all, and thirteen consecutive billing failures meant
nothing ever contradicted that. Found by the first genuinely executed run, on the release candidate.

`test/guards.test.mjs` now asserts that no glob appears in the test command and that every test file
on disk is named in it, which closes that specific hole. A matrix closes the class.

## Notes

**Deferred, not dropped, and deliberately not part of IN-02.** The adoption and enforcement work is
the higher-leverage next problem; this is hardening that should not interrupt it.

`actions/checkout@v4` and `actions/setup-node@v4` currently emit a Node 20 deprecation warning on
every run. It is informational — the warning is about the actions' own runtime, not the
`node-version` the steps run under — and rides along with this item unless GitHub attaches a
deadline to it, in which case it becomes urgent on its own.

Changing the matrix changes nothing an adopter is evaluated on: no standard, rule, policy semantic,
or evaluator behaviour is involved.
