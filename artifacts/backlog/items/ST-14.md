## What

Publish `standards-adapter.json` at the repository root: this pack's declaration of how it is invoked
and how its answer is read, conforming to StandardsEnforcer's adapter schema `1.0.0`. Guard the
declaration against the CLI it describes, so it cannot become false by an edit somewhere else.

## Why now

StandardsEnforcer records this pack as one of five **blocked** authorities, for one reason:

> | HealthAndFitnessAndNutritionStandards | yes | `project: TARGET-PROBE` | **no — no tag, `1.0.0-dev`** | **BLOCKED** |
>
> — `StandardsEnforcer@artifacts/evidence/2026-08-09-contract-expressiveness.md:17`

The contract was never the obstacle. The enforcer proved by execution that `check {target} --json`
correctly reports the target rather than this pack, and only Financial needed the `{policy}`
placeholder that forced schema 1.1.0. The obstacle was release identity, and `v1.0.0` removed it —
that row is stale.

What remains is that this pack publishes no declaration at all. Betting, Mathematics, MachineLearning
and Innovation each ship one; `scripts/enforce.mjs:76` reads `standards-adapter.json` from the pack's
own verified checkout, so without it this pack cannot be invoked no matter which tag exists.

## The declaration, and why each field is what it is

```json
{ "schemaVersion": "1.0.0",
  "standard": { "id": "health-fitness-nutrition" },
  "evaluation": { "entrypoint": "scripts/standards.mjs",
                  "arguments": ["check", "{target}", "--json"] },
  "result": { "statuses": [ …seven… ], "passing": ["COMPLIANT", "COMPLIANT_WITH_EXCEPTIONS"] } }
```

`1.0.0` rather than `1.1.0`: `{policy}` exists for packs that do not read the policy from the target,
and this one does. Declaring the later version would advertise a binding this CLI has no use for and
would make the contract unreadable to any enforcer built before 1.1.0, for nothing.

**`result.statuses` is where this could have gone wrong, and it is the reason the story has guards
rather than just a file.** The enforcer's vocabulary for this pack was recorded on 2026-08-09. FE-13
then added `UNIDENTIFIED_RELEASE` and routed self-maintenance out of `check` under
`SELF_MAINTENANCE`, and nothing connected those facts to any published contract. Copying a sibling
pack's status list — all five of them agree, and all five are wrong for this pack — would have
produced a declaration that was false on the day it shipped. An undeclared status is
`ENFORCEMENT_ERROR` at the enforcer: it fails closed and reports that *this pack's contract* is
unreadable, which is the right refusal and the wrong diagnosis.

The complete vocabulary `check` can emit is seven, not five:

| Status | Reached by | Exit |
| --- | --- | ---: |
| `COMPLIANT` | verdict | 0 |
| `COMPLIANT_WITH_EXCEPTIONS` | verdict | 0 |
| `NON_COMPLIANT` | verdict | 1 |
| `NOT_EVALUATED` | verdict | 4 |
| `BLOCKED_BY_INVARIANT` | verdict, or a blocked self-maintenance refusal | 3 |
| `UNIDENTIFIED_RELEASE` | release identity not established (FE-13) | 5 |
| `SELF_MAINTENANCE` | `check` asked of the pack itself (ADR 0009) | 6 |

## The guards

`test/adapter-contract.test.mjs`, and the design constraint on them is the owner's: they compare **two
independently meaningful surfaces**, never one constant read twice. Nothing exports a shared status
list that both the adapter and the evaluator consume — that arrangement would let one mistaken edit
update the implementation and the declaration together and stay green, which is a guard that reports
agreement with itself.

1. **`result.statuses` equals the complete top-level vocabulary `check` can emit.** Derived from
   `STATUS` in `scripts/compliance.mjs` (the verdict path) unioned with the refusal literals extracted
   from `commandCheck` in `scripts/standards.mjs` (which never pass through `STATUS`). Red in both
   directions: a new CLI status without an adapter update, and an adapter claiming a status the CLI
   cannot produce.
2. **`result.passing` equals the statuses `check` exits 0 on.** Derived from a *different* part of the
   CLI — the exit-code mapping, not the vocabulary — because these are different normative claims.
   `statuses` says what can be emitted; `passing` says which of those authorise proceeding, and the
   enforcer deliberately refuses to know that `COMPLIANT` means pass so that the pack has to say it.

Both extractions assert their own seam before comparing anything. A scan that stops matching yields an
empty set that compares equal to nothing and reports success — the failure StandardsEnforcer closed in
its own guard at `17c3fad`, *"Make the seam guard fail when it cannot find the seam"*.

## What is deliberately not done

`standards-adapter.json` is **not** added to `MATERIAL` (`scripts/release-material.mjs`). That list is
the reviewed set of paths whose bytes can change a *verdict*, and the adapter changes no verdict this
pack issues. Its integrity is the consumer's to establish: the enforcer reads it out of a checkout
whose identity the enforcer verified itself, which is the only place that check means anything. Adding
it here would widen a reviewed boundary to cover a file this CLI never reads.

## Completion

**This story does not complete when the adapter exists on `main`.** The declaration is useful to the
enforcer only inside an immutable released checkout — `readAdapter` reads it from a verified release,
and the only tag that exists (`v1.0.0` at `570c45b`) predates it. So completion evidence must include
the release that first publishes it.

That release is `v1.1.0`, and it is doing three legitimate jobs at once rather than three unrelated
ones bundled together:

- publishes `standards-adapter.json` in an immutable pack (this story);
- is the first release whose evaluator contains FE-13's identity mechanism, which is what R2
  certifies ([FE-13](FE-13.md));
- executes `docs/release-signing.md` in production for the first time ([ST-12](ST-12.md)).
