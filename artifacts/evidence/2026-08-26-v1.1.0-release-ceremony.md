# v1.1.0 — the first release signed under the regime, and everything that happened on the way

**Released 2026-08-26.** Tag object `6c8d8935d2fbe842c09569f4530fd0c16dc91446`, dereferencing to
release commit `91c870087c32d8b728249aa91cc1659b7eadf979`.

This record is written **after** publication, on post-release `main`, and deliberately so: the
certified object must not change to accommodate the record of its own certification. It carries four
things that would otherwise be scattered — the blocker that held the release, a near-miss during
setup, the R2 evidence block, and the outcome.

## 1. The blocker, and why it was not a defect

For part of 2026-08-26 the release was stopped here:

> `v1.1.0` is blocked on initial establishment of the human-controlled release-signing identity and
> its independently registered public trust anchor. This is a governance event, not a repository
> defect.

The candidate was already verified and waiting. What did not exist was the identity. Established by
inspection that day: nothing signing-related configured at any Git scope — `user.signingkey` and
`gpg.format` both unset, so a bare `git tag -s` would have reached for GPG rather than SSH — no
`~/.ssh` directory at all, no running ssh-agent, no `allowed_signers` file anywhere, and no anchor in
StandardsEnforcer either.

**No repository change could have lifted it, and that is the point rather than an inconvenience.**
ADR 0010 puts the private key with the custodian and forbids the pack generating it; ADR 0011
requires the anchor to reach the verifier from outside the evaluated pack. An agent creating either
would have produced a release whose provenance was the agent's session — the exact property the
signature exists to deny a fork, arriving as an administrative convenience rather than as an attack,
which is the shape ADR 0010 §8 names.

The blocker was lifted by a human act, not by code: a dedicated `hfn-release-signing` ed25519 key
under the custodian's control, its public half placed in the operator trust store now recorded in
[ADR 0013](../adr/0013-the-trust-anchor-lives-in-an-operator-store-outside-every-pack.md).

**A dedicated key rather than a reused authentication key**, decided by the custodian. It gives the
anchor one meaning — *the authority to publish these standards* — and keeps two revocation stories
apart. A lost laptop would otherwise force a release-key rotation, which ADR 0010 makes a governance
event, over an incident with nothing to do with release authority.

## 2. The near-miss, recorded because it was close rather than because it landed

While probing for signing tooling, the agent ran `ssh-keygen -h` expecting a help flag. It is not
one: OpenSSH treats the unrecognised argument as a request to generate, printed *"Generating
public/private ed25519 key pair"*, and blocked at the filename prompt. It was terminated there.

**Nothing was written.** Verified immediately afterwards: `~/.ssh` still absent, no key files in
`$HOME`, no `ssh-keygen` process remaining. The version check was then done safely with `ssh -V`
(OpenSSH_10.2p1).

Worth recording for one reason: **the only thing that prevented a key from being created was the
prompt blocking on a null stdin, not the command being safe.** This happened under an explicit
instruction not to generate a key. A tool-availability probe should not be capable of creating state,
and the lesson is to probe with something that cannot write — `ssh -V`, or `command -v`.

**No guard was added, and none should be.** The test for a new guard in this repository is whether a
mechanically enforceable property follows, and none does: this was a command choice made by an agent
in its own session, not a property of the pack. HFN cannot check what flags an agent passes to an
unrelated binary. Recording it as an operational fact is the whole remedy; inventing a check that
cannot see the thing it names would be worse than nothing, because it would read as coverage.

## 3. R2, as emitted

Run while the tag existed locally and was still unpublished, with the anchor read from the operator
trust store into the environment. Exit 0.

```text
candidate commit                      91c870087c32d8b728249aa91cc1659b7eadf979
annotated tag object                  6c8d8935d2fbe842c09569f4530fd0c16dc91446
dereferenced release commit           91c870087c32d8b728249aa91cc1659b7eadf979
signature present on the tag          yes
signer fingerprint                    SHA256:ZIKVolJl/xr0Z8lNvxjUDh0EvG+XUS1D0v+OCqRf26k
local external verification result    verified under HFN_TRUSTED_PUBLIC_KEY
R2 result                             PASS — control established identity; modified material refused as material-differs
tag pushed at time of R2              no
```

The last line is the one the whole ordering exists to make true, and it was corroborated
independently of the script: `git ls-remote --tags origin` **succeeded** and returned empty. An
unqueryable origin would have been a different answer — `R2 INCOMPLETE`, exit 2 — and the distinction
between *checked and absent* and *could not check* is the finding that independent review of PR #8
put into this script.

The `R2 result` line is the substantive one. A control run established identity, and the same
release with one byte of material altered was refused as `material-differs`. That is FE-13's subject
discharged against the real release rather than against a fixture.

## 4. The candidate, and why the merge commit was verified in its own right

The release commit is the PR #8 **merge** commit, whose tree is byte-identical to the reviewed head
`6c1c278` — `274ba0a` was already an ancestor, so the merge introduced no unreviewed content.

The full container gate was nonetheless run on `91c8700` itself rather than inferred from its parent:
8/8 stages, `300 tests, 296 pass, 0 fail, 4 skipped`. The four skips are environment guards named
rather than assumed — one Docker-in-Docker assertion and three `ci.ps1` tests that require Windows —
and all four run green on the host, where the same suite is `300 pass, 0 fail`. Between the two
surfaces every test executed; neither surface alone did.

Tree identity was a fact **discovered by checking**, not a licence to skip the check. Hosted CI was
green on the same SHA (run `32881414337`).

| Published | 2026-08-26, after R2 and not before |

`v1.1.0` is the first release for which this pack can say a signature was made by an identity a fork
cannot hold, checked against a key a fork cannot replace. That is the floor ST-12 argued for and
could not establish from inside the pack, and it begins here rather than retroactively
([ADR 0008](../adr/0008-authenticity-guarantees-are-not-retroactive.md)).

**What is still not claimed.** Full-fork exclusivity remains outside this repository. The trusted
execution boundary lives in StandardsEnforcer, and until it implements the host contract, reads the
anchor from outside the pack, and passes the hostile-fork vector from that boundary, the
portfolio-level origin guarantee is undelivered. Nothing here may report otherwise.
