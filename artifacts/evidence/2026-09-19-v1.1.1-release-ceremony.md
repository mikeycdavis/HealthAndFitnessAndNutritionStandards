dereferencing to release commit `0ca5707b5d5d5e1491901a2a1df21af2045d946b`.

Written **after** publication, on post-release `main`, for the reason the 1.1.0 record gives: the
certified object must not change to accommodate the record of its own certification.

## 1. What the release is

A **patch**. `standards/`, `rules/`, `schemas/`, `templates/`, `PROHIBITIONS.md` and both inventories
are byte-identical to `v1.1.0`. Inside the release-material boundary exactly one thing changed
besides the version: a guard in `scripts/backlog.mjs` that refuses to recreate a file backlog in a
GitHub-authority repository. `VERSION` is itself material, so the bump had to land before the tag,
and R2 checks the tag against it.

The release commit is the PR #57 **merge** commit. Its tree, `45f769c78c62…`, is identical to the
reviewed head `234f63b`, so the merge introduced no unreviewed content. That was checked, not assumed.

## 2. The key rotation — a governance event (ADR 0010 §8)

`v1.1.0` was signed by a dedicated `hfn-release-signing` key. Before this release the custodian could
no longer supply that key's passphrase. **The key was not compromised, and nothing suggests it was.**
It was made unusable by a lost passphrase, which is a different fact from a leaked secret and is
recorded as one: the old key is **retired**, not revoked.

The custodian generated a new dedicated ed25519 key and replaced the active anchor in the operator
store (ADR 0013) — the deliberate act that grants authority — after copying the old anchor aside.
No agent generated, held, or read either private key. The old private key was never opened.

### What the rotation does to earlier releases, established by running it

Each tag was verified under each public key with `ssh-keygen -Y verify`:

```text
v1.1.0 under the retired anchor : exit 0    Good "git" signature ... SHA256:ZIKVolJl/...
v1.1.0 under the active anchor  : exit 255  Could not verify signature.
v1.1.1 under the active anchor  : exit 0    Good "git" signature ... SHA256:Ms8cz3LU...
v1.1.1 under the retired anchor : exit 255  Could not verify signature.
```

**A host that reads only the active anchor cannot verify `v1.1.0`.** The trust store holds one key per
pack, so rotating it moved the answer. Keeping the retired key beside it preserves the ability to
verify history for anyone who applies it explicitly; it does not make the active anchor accept the
old signature, and it must not be read as if it did. `certified-releases.json` records each release's
signer, so lineage stays accurate.

**Undecided, and not decided here:** whether the host contract should carry retired anchors for
historical releases. Until it does, verifying `v1.1.0` against a rotated anchor is a host
decision, not a property of this pack.
