# 0010 — The release signing key has a human custodian, and the trust anchor comes from outside the pack

- **Status:** Accepted
- **Date:** 2026-08-16
- **Deciders:** project owner (Michael Davis), as the accountable human release owner — deciding the
  key-custody question [ST-12](../backlog/items/ST-12.md) was deferred on

## Context

[ADR 0009](0009-self-maintenance-is-a-distinct-outcome.md) closed the copied-evaluator escape and
named the residual it did not close: a fork of this repository possesses every byte the original does
— the certified tag, the recorded oid, the lineage, and the file explaining them — so no check running
inside the evaluator distinguishes a fork from the pack. The owner's approved acceptance boundary
retired the absolute criterion and assigned that residual to ST-12.

ST-12 was deferred for one reason above the others: it is a key-management commitment rather than a
code change, and nobody had decided who holds the key. That question is answered here, along with a
second one that was not being asked and would have been the more expensive omission.

**A signature verified against a key the fork also controls establishes nothing.** If the trusted
public key or fingerprint lives only inside this repository — `scripts/trusted-key.json`, say — then a
fork replaces that file with its own key, signs its own tag with the matching private key, and
verifies successfully. The result reads as cryptographic proof of origin and is proof of nothing but
internal consistency. It would be the FE-13 defect rebuilt one layer up and wearing a stronger name:
the pack authenticating itself against material it supplies, which is precisely the false authority
FE-13 exists to remove.

So the trust anchor cannot come from the pack being authenticated. That is a constraint on the design
rather than a feature of it, and it is frozen here before implementation because it is not visible in
a passing test written the obvious way.

## Decision

### The model

```text
Accountable human release owner
        │
        │ controls private release-signing key
        ▼
signed immutable release
        │
        ▼
pack presents tag + signature
        │
        │
        ├──────── pack contents / claimed key   ← NOT authoritative
        │
        ▼
external trusted fingerprint / public key
        │
        ▼
signature verifies?
     /       \
   yes        no / unavailable
    │              │
    ▼              ▼
origin           FAIL CLOSED
established
```

### The eight decisions

1. **Custodian.** Michael Davis, as the accountable human release owner. Not an agent, not GitHub
   Actions, not the repository. Custody is an accountability relationship, and the other three
   candidates are things rather than people.
2. **The private key is human-controlled.** Never committed, never generated by the pack, never
   exposed to ordinary CI. Its job is narrow: authorize immutable standards releases. A key that
   ordinary CI can exercise is a key every workflow-file author can exercise.
3. **The trust anchor is supplied externally to the pack being evaluated** — from an operator-
   controlled trust store or a centrally governed trust configuration such as StandardsEnforcer's,
   never from a file inside the material under evaluation.
4. **Release authorization.** Only an immutable release signed by that trusted key can establish
   canonical-pack origin. Lineage membership remains what it already is: a fact about history, not a
   fact about origin.
5. **No configured trusted key is `NOT ESTABLISHED`** — never "signature verification skipped". The
   distinction between *contradicted* and *unavailable* that `scripts/pack-lineage.mjs` already keeps
   is extended here, and unavailable still fails closed. A check that reports success when nothing is
   configured is the exact false green this line of work exists to remove.
6. **A wrong or untrusted signature fails closed.** There is no degraded mode, no warn-and-continue,
   and no fallback path. The temptation to add one is why ST-12 was not implemented half-configured.
7. **Key rotation is an explicit governance event.** A new key is not accepted merely because the
   repository contains it — that is the substitution attack the falsifier below exists to catch, and
   accepting it silently would make the anchor's externality decorative.
8. **Agents may verify signatures and prepare release material. They may not possess or exercise the
   human release-signing authority.** This repository already holds the general form of that rule —
   an agent may draft the analysis behind an attestation and may never write a name into
   `reviewedBy`. Analysis can be delegated; accountability cannot. A signature is an attestation with
   a harder edge, so the rule applies with more force, not less.

## The falsifier this must be designed around

Written before the mechanism is chosen, because it is what selects between mechanisms rather than
something to check afterwards:

> Copy the entire repository, replace its trust configuration with an attacker-controlled public key,
> create a correctly signed release using the attacker's matching private key, and prove that
> verification still rejects it because the authoritative trust anchor came from outside the fork.

The fork in that test is not incompetent. It signs correctly, it verifies its own signature
correctly, and every artifact it holds is internally consistent. It fails on exactly one fact: the
anchor is not its to change. **If a proposed implementation passes only because the fork did not think
to replace the key file, it has not met this criterion** — it has rebuilt the problem FE-13 just
removed, with a better vocabulary.

## Where the requirement binds: `maintain` reports origin, consumers of origin require it

Decided by the owner on 2026-08-16, after the question was raised as the last thing blocking
implementation.

> **Self-maintenance eligibility remains lineage-based. Canonical-origin authenticity is
> independently evaluated and reported. Absence of an external trust anchor does not prevent
> `maintain` from evaluating the working tree, but it must prevent any positive origin claim.**

`maintain` is not an origin-authority operation. Its job is to answer whether this working tree
satisfies the standards it publishes, under a status that is deliberately not an adoption verdict.
Requiring an external anchor before that question may be *answered* would make ordinary development
depend on release-owner credentials or operator trust configuration that contributors correctly
should not possess — ADR 0009's unachievable gate, arriving from the other direction.

So fail-closed binds at the origin claim, not at the evaluation:

| Situation | `origin.status` | `origin.reason` |
| --- | --- | --- |
| externally trusted key + valid authorized signature | `ESTABLISHED` | — |
| no external trust anchor | `NOT_ESTABLISHED` | `trust-anchor-absent` |
| wrong signer | `NOT_ESTABLISHED` | `untrusted-signer` |
| invalid signature | `NOT_ESTABLISHED` | `invalid-signature` |
| required signed release cannot be resolved | `NOT_ESTABLISHED` | `release-unavailable` |

None of these may silently become `ESTABLISHED`, and **none may be inferred from lineage alone** —
lineage answers a different question and answering it well is not evidence about origin.

**The state is named, not boolean.** `originVerified: false` was rejected: a boolean invites callers
to collapse "checked and rejected", "could not check", and "no anchor was supplied" into one branch,
and the whole reason this mechanism is worth building is that those three mean different things to
whoever has to act on them.

**Where it does bind as a requirement:** any command or umbrella operation that claims canonical pack
origin as a prerequisite. If an enforcer eventually says "this project was evaluated against the
canonical Health/Fitness/Nutrition pack", `origin.status !== ESTABLISHED` fails closed there. That
consumer is making the cryptographic claim; `maintain` is not.

**The separation is structural, not documented.** ADR 0009's property 2 was a true statement placed
where consumers do not look, and appending origin metadata in the hope downstream callers read it
would repeat that with better vocabulary. Any API making an origin-dependent assertion goes through a
contract that requires `ESTABLISHED`, and the tests prove that reading only `status` or
`workingTreeStatus` can never yield a positive canonical-origin result.

## What is not claimed

**Signing the historical `v1.0.0` tag would not make a fork of that signed history non-canonical.** A
fork can copy a genuine signed historical tag exactly as it copies everything else; a signature proves
who authorized an object, not who is holding it now. The authenticity property becomes strongest at
the first *new* release signed under this regime: from that point a fork can copy already-authorized
releases but cannot mint a new authoritative one without the custodian's private key. This is
[ADR 0008](0008-authenticity-guarantees-are-not-retroactive.md)'s fact arriving a third time —
guarantees attach to the release that declared them — and it is stated in advance so it is not
discovered as a surprise instead.

**The property is relational, not absolute.** What verification establishes is "this release was
authorized by the key *this operator independently trusts*". For an operator who obtained the
fingerprint from the pack, it establishes nothing at all, and no code inside the pack can tell those
two operators apart. The externality of the anchor is therefore a property of the deployment, which
means it has to be documented for adopters rather than enforced for them — the honest claim is narrow
and stating it narrowly is the point.

## Alternatives considered

### Rejected: ship `scripts/trusted-key.json` inside the pack

The convenient design, and the one a reasonable implementer arrives at by default: it needs no
operator configuration, it makes the falsifier easy to write, and every test passes. It authenticates
the pack against a key the pack supplies. Recorded as rejected rather than omitted, because its
absence would otherwise look like an oversight to the next person holding the problem.

### Rejected: give ordinary CI the signing key so releases can be automated

It would make releases cheaper and would move the custody from a person to a workflow file, which is
to say to everyone who can edit one. Decision 2 exists because release authorization is the one
capability this repository has that should be expensive.

### Deferred, deliberately: the cryptographic mechanism

GPG, SSH-key signing, minisign, or something else is not decided here. Choosing plumbing before the
falsifier exists is how a mechanism gets adopted for its ergonomics and then rationalized. The
falsifier above is what any candidate must be measured against, and it is stated in terms no
particular tool supplies.

## Consequences

- ST-12 is no longer deferred: its blocking question is answered, and its acceptance criteria are
  rewritten around the substitution falsifier.
- `scripts/certified-releases.json` will need to record, per release, whether it was signed under this
  regime and against which key identity — a release predating it must be able to say so rather than
  be silently treated as unsigned-therefore-fine or unsigned-therefore-broken.
- `maintain` reports origin and does not require it; anything claiming canonical origin requires it.
  Both invariants are preserved by that split: development stays achievable without release
  authority, and origin authority stays impossible without an externally supplied anchor.
